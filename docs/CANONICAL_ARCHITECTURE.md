# Canonical architecture

The rule text is `docs/RULEBOOK.md` (versioned, mirrored byte-for-byte into the iOS repo, stamped into the packed script by `rulebookStamp()`). This file is the technical reference: paths, modules and how each platform calls them.

Web and iOS are separate repositories and separate languages. They share one executable business core. Screens, navigation, and platform persistence stay in each app.

## Paths

| Piece | Path |
|---|---|
| Canonical core | `project-planner-web/lib/canonical/` (`engine.ts` for windows, organisation, the standard day and its AM/PM halves, slot intervals, and session company choice (`chooseSessionOrganization`, `orgAccessProbeFromReads`, `sessionMembershipIds`); `organizationSettings.ts` for org-wide defaults, payment-run field names, warningDetection, payroll, leave defaults, schedule options, and the organisation material cut-off clock (`parseMaterialCutOff`, `resolveMaterialCutOffClock`); `billingAccess.ts` for whether the organisation still has product access (`hasAccess`) from `organizations/{orgId}.billing`; `timesheetSubmission.ts` for the timesheet submit deadline and reminder notify-at derived from a payment day (close of play the day before; 08:00 three days before), generated notice copy, and which occurrence is due; `timesheetPeriod.ts` for timesheet period identity (org + user + start/end day keys), Awaiting / Signed off / Exported (`timesheetListBucket`), sign-off and export write fields (`managerSignedAt` + `approvedAt` alias, `exportedAt`), and selectable historical + current payment-run periods (`selectableTimesheetPaymentRunPeriods`); `warningRows.ts` for which qualification, unverified, and unbooked warnings exist and the qualification dismiss key; `warningSort.ts` for display order of already-computed warning rows by coverage `dayKey` (`oldest` / `newest`); `leaveCoverage.ts` for annual leave against bookings; `staffAccess.ts` for who sees every job, every warning, and every variation, who may edit a work catalogue, who may open User Timesheets (`canReviewUserTimesheets`, `seesEveryUserTimesheet`), who sees a job's quote and order history (`canViewMaterialOrderHistory`), and which managers receive a job notification; `userTimesheetAccess.ts` for whose timesheets a viewer sees on User Timesheets and whether the screen opens (`userTimesheetSubjects`, `canOpenUserTimesheets`); `materialWhatsApp.ts` for the Send via WhatsApp message, the wa.me number and the landline refusal (`materialWhatsAppRows`); `materialOrderRecipients.ts` for who receives the `material_order_placed` inbox row (`materialOrderRecipients`); `userRosterSegment.ts` for Active / Inactive / Pending (`userRosterSegment`, `matchesRosterSegment`, `listedRosterUsers`); `inviteEmailClaim.ts` for whether a re-invite is blocked (`resolveInviteEmailClaim`); `userProfile.ts` for the `users/{uid}` document, employment-type day, and Edit User permission copy; `notificationPreferences.ts` for user-level inbox toggles on `users/{uid}.notificationPreferences`, which My notifications rows appear (`visibleNotificationPreferenceKeys`, `notificationPreferenceCopy`), the shared inbox destination kind, which inbox types send one FCM device push (`devicePushNotificationTypes`, `notificationDeliversDevicePush`), and the shared unread badge (`unreadNotificationBadgeCount`); `annualLeaveBalance.ts` for allowance vs year-count, the leave year, and a one-year remaining override; `materialSearch.ts` for catalogue search ranking; `materialDelivery.ts` for the default required-delivery instant on a material **order** (tomorrow 08:00, or Monday 08:00 when Send is opened on Saturday or Sunday) and that a **quote** never includes a day or time; `qualificationSearch.ts` for organisation qualification library search and section chips; `operativeQualifications.ts` for assigned qualification write shape, certificate URL merge, and the certificate storage path) |
| Web consumption | Import `@/lib/canonical`. Existing modules such as `lib/warnings/warningLookahead.ts`, `lib/orgMembership/webActiveOrg.ts`, `lib/timesheets/timesheetWeekUtils.ts`, `lib/permissions.ts`, `lib/access/workAccess.ts`, and `lib/stripe/billing.ts` (`hasAccess`) call that module instead of keeping a second copy. |
| iOS consumption | `Project Planner/Canonical/canonical-business.js` is the bundle built from `lib/canonical/bundleEntry.ts`. `Project Planner/Canonical/CanonicalBusinessEngine.swift` evaluates it. Warning scans and invoicing defaults use that result, with `Europe/London` when the script cannot load. |
| Bundle command | `npm run build:canonical` in the web repo. `npm test` rebuilds it. |
| Backend | Firebase security rules are the server-side organisation boundary: `project-planner-web/firestore.rules` only (the iOS repo keeps no copy). Why each rule is written as it is: `docs/firestore-rules-notes.md` (the rules file carries no comment blocks, to stay small enough to compile). Indexes: `firestore.indexes.json` (notifications `userId` asc + `createdAt` desc). Email is the authenticated HTTP function `sendEmail` in `functions/email` (same codebase `inbox-push`; contract in `docs/EMAIL_FUNCTION.md`): a Firebase ID token and organisation membership (`organizationMemberActive`, `organizationLevelFor`), fixed templates rendered in the function, recipient rules (invitation email, active members, the organisation's `wholesalers` contacts via `parseWholesalerDocument`), PDF/XLSX/CSV attachments up to 10 MB, a per-sender rate limit (`emailRateLimits/{uid}`); web API routes call it with the server key. The old open `sendProjectPlannerEmail` was deployed from outside this repo and is deleted by the owner once both apps call `sendEmail`. Device push is `functions/` in this repo (`firebase.json` codebase `inbox-push`): `sendDevicePushOnNotificationCreate` on create of `organizations/{orgId}/notifications/{id}`. It loads the packed rulebook and must not copy the allow-list or unread counter. After `sendEachForMulticast` it drops only tokens whose result is invalid APNs credential, unregistered, or invalid registration token (`functions/prunePushTokens.js`); accepted tokens stay, and one failure must not clear `users/{uid}.pushTokens`. Deploy with `firebase deploy --only functions:inbox-push`; that neither replaces nor deletes `sendProjectPlannerEmail`, which is not in this codebase. Web never requests browser notification permission and never sends a browser or OS notification. |
| Bookings | `lib/canonical/bookings.ts`. `parseBookingDocument(docId, data, { timeZone })` is the one reader: it returns the booking (dates as milliseconds) with any legacy `repairs` (`status_alias`, `slot_missing_full_day`, `slot_alias`, `operative_id_alias`, `project_id_alias`, `booked_by_missing`, `date_not_timestamp`), or the refusal `errors` (`missing_operative_id`, `missing_project_id`, `missing_date`, `bad_status`, `bad_time_slot`). `BOOKING_STATUSES`, `BOOKING_TIME_SLOTS`, `normalizeBookingStatus` and `normalizeBookingTimeSlot` are the only status and slot lists; `isOpenBookingStatus` (Confirmed or Tentative) is a booking still on the job, used for a job's active subcontractors; `bookingClock` reads text or stored-instant clocks in the organisation zone. `bookingWriteFields` is the one write shape; each app converts `date`, `createdAt` and `updatedAt` to its Timestamp. `operativeIdIsUuid` flags ids iOS cannot hold in a Swift `UUID`. Deleting a person removes `bookingsToRemoveOnOperativeDelete` (their user id and operative ids, dated today or later in the organisation zone; never by name; deactivating removes nothing). Deleting a job removes `bookingsToRemoveOnProjectDelete` (today or later); past bookings stay and show `bookingJobLabel` / `ORPHAN_BOOKING_LABEL` ("Deleted job"), with `bookingJobState` for the check. Data Health's admin scan is `bookingHealthRows`. Web: `parseBooking` / `serializeBooking` wrap these; `lib/bookings/removeBookingsOnDelete.ts` runs the delete rules. |
| Schedule sources | `lib/canonical/scheduleSources.ts`. What each app loads, who a booking belongs to, which jobs count, and where approvals live. `rosterPeople(docs)` folds `users` documents to one row per email: the admin document is kept, then the signed-in one, then the newer `updatedAtMs`, then the active one, then the higher `rosterDocumentRank`, then the lower id; the other ids go on `sameEmailUserIds` and into `userIdAliases` (folded id → kept id), and former invite ids are merged. `bookingLoadStart` is the first booking day to download (the earliest needed day; an earlier warning window reloads; `fullHistory` means no lower bound — web loads whole collections). `workDocuments(projects, smallWorks)` keeps every job document once by id only (two documents may share a job number such as "C646"; the `INITIAL-PLACEHOLDER` document is not a job); `workStatusOn` / `isWorkLiveOn` are calendar-day status from `isLive` and the start / end day keys (a job ending today still runs today). `personDayItems` lists each active manager or admin's bookings per day (manager-schedule bookings and labour bookings), reading every stored id through `resolveBookingPerson`; `managerClashGroups` is the clash groups from `slotInterval` and `overlappingIntervalGroups`, with `pairKey`, the accepted-pair booking ids and `resolutionKey` (`mgr-clash-{userId}-{dayKey}-{index}`). `clashPairKey`, `isClashAccepted` (id or the two booking ids, either order, without case) and `acceptedClashWriteFields` are `organizations/{orgId}/acceptedBookingClashes/{pairKey}` (the app adds `acceptedAt`). `warningResolutionWriteFields` is `organizations/{orgId}/warningResolutions/{resolutionKey}` with `resolutionKey`, `status` (`approved` / `dismissed`) and `resolvedByUserId` (the app adds `resolvedAt`; undoing an approval deletes the document). `resolvedWarningKeys(records)` reads those documents back (status `approved` / `dismissed`, any case; key is `resolutionKey`, else the document id). `isWarningActive(row, { resolvedKeys, acceptedClashes })` decides whether a computed warning row still counts: hidden when its resolution key is resolved or, for a clash row, its booking pair is accepted. The warning total on both apps is the number of rows it keeps, after expired qualifications in `dismissedWarnings` (`withoutDismissedQualificationRows`). Web resolution keys are the rulebook row ids (`unbooked-…`, `leave-…`, `qual-…`, `unverified-…`) and the manager-clash `resolutionKey`. Web: `activeOrgWarnings` (`lib/warnings/generateOrgWarnings.ts`) applies it for the Warnings page and the Home tile, and `lib/warnings/warningResolutionStorage.ts` reads the collection; `dedupeUsersByEmail` / `aliasIdsForRoster` (`lib/staff/userRosterUtils.ts`), `mergeProjectsAndSmallWorks` / `deriveWorkStatus` (`lib/projects/workStatus.ts`), `computeManagerBookingClashWarnings` (`lib/warnings/managerClashWarnings.ts`) and `lib/warnings/acceptedClashStorage.ts` call these. |
| Parity fixture | `lib/canonical/parity-fixture.json`: cases of `{ name, function, args, expected }` for every schedule-source function. `lib/canonical/canonical.test.ts` runs each case against the TypeScript module and the packed script. `npm run build:canonical` copies it to iOS `ProjectPlannerTests/CanonicalParityFixture.json`, `--check` refuses a stale copy, and the pre-commit hook refuses a web commit while that copy is uncommitted. iOS runs the same cases through `CanonicalBusinessEngine`. A new expected value is changed in the fixture, never in one app's test. |

## What is shared

The canonical module owns:

- Organisation id matching and which company a session should open (`chooseSessionOrganization`, `provisionalOrganizationId`, `orgAccessProbeFromReads`, `sessionMembershipIds`). Remembered keys: web `pp.webActiveOrg:{userId}`, iOS `cached_organizationId`. Same-user sign-out must not clear them (`shouldClearRememberedOrganization`). The switcher always keeps remembered / user-document / explicit companies even when a members query finished without them. Company name is `parseOrganizationName` / `organizationNameWriteFields` — a blank write is omitted so `name` cannot be wiped.
- The in-process organisation epoch used to drop a late result after a switch or sign-out
- Invoicing-period bounds, including wrapped payment runs and short months
- Organisation settings defaults and Firestore field names (`organizationSettings.ts`): payment runs write **both** `startDay`/`endDay` (web) and `startDate`/`endDate` (iOS); read prefers the iOS pair when both exist and disagree (`normalizePaymentRunRange`); empty ranges are 1–15 then 16–31; warningDetection is the top-level org map; payroll weekend hours use iOS field names; the material cut-off clock is `resolveMaterialCutOffClock` / `parseMaterialCutOff` on `settings.materialCutOff` (user-pref hour is never the clock)
- Who sees variations (`canSeeVariations`): every admin and manager, never an operative
- Warning coverage windows (`numberOfDays`, full Monday–Friday week, invoicing period)
- Whether a person covers the organisation standard day (`standardDayCoverage`). A full day (`FULL DAY` / `FULL_DAY`) covers 07:30–16:00 minus the unpaid break even when clock times are missing. Bookings match the person by user id or operative id. A shorter booking stays unbooked and the missing hours are the gap. Weekend days are included only when `warningDetection.includeWeekendsForUnbookedLabour` is on. That toggle and `warningDetection.excludedUserIdsFromUnbookedWarnings` apply to **both** the Warnings list and Daily Overview — Daily Overview must not keep a weekday-only unbooked gate.
- Organisation time zone for those windows (default `Europe/London`, never the device zone)
- Named booking slots (`FULL DAY` / `FULL_DAY`, `AM`, `PM`) and their pay (`paidHoursForNamedSlot`)
- The standard day and its two halves (`standardDayWindow`, `halfDayWindows`), and the clock interval any booking occupies (`slotInterval`). See "Standard day, AM and PM" below
- Whether two minute intervals clash, and interval merge / subtract (`intervalsOverlap`, `mergeMinuteIntervals`, `subtractMinuteIntervals`)
- Cache key shape `kind:organizationId`
- Which qualification warnings exist, which operatives are unverified, and which people are unbooked labour (`qualificationExpiryRows`, `unverifiedOperativeRows`, `unbookedLabourRows`). Daily Overview's "today" list is `unbookedLabourRowsOnDay` — the same rows for one day, not a second person loop. `includeWeekendsForUnbookedLabour` and `excludedUserIdsFromUnbookedWarnings` on `organizations/{orgId}.warningDetection` apply to Warnings **and** Daily Overview. An anonymised deleted profile (`isAnonymisedDeletedProfile`) is never a current warning, Daily Overview unbooked row, new weekly-report warning, or scheduling / book-labour candidate (`listedCurrentLabourPeople`). Historic bookings keep the stored name.
- Booking identity across Scheduling, Daily Overview, Warnings, and the weekly report (`warningRows.ts`):
  - `bookingOccupiesDay(status)`: Confirmed, Tentative (and the `pending` alias), and Completed put a person on a job that day; Cancelled does not. No screen keeps its own status list.
  - `labourBookingKind(person)`: `operative` (operative-mode account, booked in `bookings`), `manager` (manager / admin / super admin, booked in `managerSiteBookings`), or `null` (not labour). The scheduling picker offers exactly the people `unbookedLabourRows` can flag. A user with no role flags is not labour on either side.
  - `labourPersonIds` / `formerIdAliases`: a booking, leave row, or warning exclusion stored under an invite placeholder id still belongs to the person after sign-up moves them to `users/{authUid}`. `LabourPerson.formerIds` is read from `users/{uid}.formerUserIds`.
  - Daily Overview never hides a booking because its person cannot be named; it lists the row as "Unknown person".
  - Whose booking it is (`bookingPerson.ts`): a stored `operativeId` may be a catalogue id, a users id (Firebase Auth uid), a former invite id or a same-email account id. `bookingIdsForAccount(account, operatives)` lists every id one account's bookings may carry (timesheets, payroll, job visibility, home job count). `resolveBookingPerson(operativeId, { accounts, operatives })` names the account and catalogue row behind one booking (weekly report, warnings names, notifications). `bookingPersonKey` is one grouping key per person, so operative clash warnings see a re-added person's bookings under the old and new ids together. A booking no person matches stays on every list. The roster lists one account per email and keeps a map of the other same-email users document ids to the one it kept (web `useOrgUserStore().userIdAliases`); `rosterAliasIdsFor(accountId, aliases)` turns that map into the account's `aliasIds`, so the weekly report names a booking stored on the other profile the same way Daily Overview does instead of "Unknown".
  - `parseManagerSiteBookingDocument` is the one manager-booking reader on both apps: it needs `userId`, a date and a manager slot; a missing or unknown `locationType` reads as `project` with a repair.
- Display order of already-computed warning rows (`sortWarningsByDate`, `parseWarningsSortDirection`, `compareWarningDayKeys`). The sort key is the row's `dayKey` (the calendar/coverage day the warning is about — expiry day for qualifications, the booked/unbooked/leave/clash/material day for the others). Default is `oldest`. A blank or invalid `dayKey` sorts last either way. This does not hide rows or change detection. The Oldest/Newest choice is local to each device and signed-in user (web `localStorage` key `warningsSortDirection:{userId}`; iOS UserDefaults keyed by user id). Load it before the Warnings list paints; persist immediately on toggle; default `oldest` only when that user has never chosen on this device — never silently fall back after they have. ## Standard day, AM and PM

One rule decides where the morning ends and the afternoon starts for a **stored** AM / PM booking. Clash detection, the calendar export, Home "up next", and the iOS clash scans call `halfDayWindows(payrollTimePolicy)`. Rulebook 1.20.0: Monday–Friday bookings are Full day or Custom only, so this is the legacy booking split; annual leave uses `leaveHalfDayWindows` (the exact middle of the day, ignoring the break: 06:30–14:30 → AM 06:30–10:30, PM 10:30–14:30) in `leaveCoverageRows`, `bookingLeaveConflicts`, timesheet leave lines and every leave label, and a stored AM / PM booking compared with leave is that leave half (`leaveComparableInterval`).

1. The standard day is `[standardDayStart, standardDayEnd)`. An unparsable or inverted pair falls back to 07:30–16:00, so no setting can produce an empty or negative half. A break field the organisation never set falls back to 12:00–12:30 (`standardBreakWindow`); that is the unpaid break `standardDayCoverage` subtracts for unbooked labour, whether or not it also splits the day.
2. If the break window is valid, strictly inside the day, and leaves at least 60 minutes on each side, it is the split: AM = `[dayStart, breakStart)`, PM = `[breakEnd, dayEnd)`. The break belongs to neither half. Default company: AM 07:30–12:00, PM 12:30–16:00. 07:00–17:00 with a 12:30–13:30 break: AM 07:00–12:30, PM 13:30–17:00.
3. Otherwise the day splits at its wall-clock midpoint, floored to the minute. A company on 13:00–19:00 that left the break at 12:00–12:30 gets AM 13:00–16:00, PM 16:00–19:00. A break jammed against one edge (08:00–08:30) is ignored for the split for the same reason.
4. FULL DAY is the whole standard day. Custom hours are the clock times stored on the booking. Evening is the four hours after the day; overtime the two hours after that.
5. Pay is unchanged: a stored AM and PM each pay half `weekdayPaidHours` (1.20.0: derived — finish − start − the unpaid break — for a policy saved from 1.20.0, else the stored `standardPaidHours`). The windows above decide clashes and cover, not money.

Because a stored AM / PM booking is the matching leave half when compared with leave (`leaveComparableInterval`), an AM booking never clashes with PM leave, and a PM booking never clashes with AM leave.

## Paid hours

`payrollHoursResult` (`lib/canonical/payrollHours.ts`) is the one hours calculation for Daily Overview, Book Labour, scheduling breakdowns, clash rows, the weekly report, timesheets, and invoicing, on web and iOS. Daily Overview and My Schedule show `workedHours` (`estimatedWorkedHours`): hours worked, never multiplied, and on a defined weekend window the clock time rather than the credited hours. Daily Overview's Standard and Overtime tiles are `workedHoursSplit` (hours worked inside and outside the standard window, adding up to `workedHours`; an all-hours weekend day is all overtime), labelled with that day's `payrollOutsideMultiplier`. The Weekly Report, timesheets and invoices use `totalPaidHours` (`estimatedPaidHours`). Neither Daily Overview nor My Schedule shows money. The unpaid break comes off only when the booking spans the break window. A stored clock pair wins over a named FULL DAY (`slotInterval`); AM and PM always pay the half. Weekly-report day units are `reportDayValue`; subcontractor days are `subcontractorDayValue`. Book Labour hides a person whose bookings cover the standard day (`standardDayCoverage`), the same rule as `unbookedLabourRowsOnDay`, not a paid-hours total. `isActiveBookingStatus` is `bookingOccupiesDay`, so Completed bookings count everywhere. Clash groups are `overlappingIntervalGroups` over `slotInterval`.

A weekend day the company never saved is `DEFAULT_SATURDAY_PAYROLL` (07:30–13:00 counts as 8 hours, time outside at 2×) and `DEFAULT_SUNDAY_PAYROLL` (every hour at 2×, not the same as Saturday), the iOS `OrgPayrollTimePolicy.default`. `parsePayrollPolicy` uses them for a missing policy and for a missing `saturday` / `sunday` map; a saved map that leaves a field out reads it as iOS `OrgWeekendDayPayrollSettings.fromFirestore` does (07:30–16:00, 8 hours, 1.5×). Booking editors (`HoursTimelinePicker`, `BookingEditSheet`, `QuickAddBookingSheet`, `DailyOverviewBookingSheet`, `SubcontractorBookingEditSheet`, `ProjectScheduleWeekOverview`) pass the organisation policy and the booking day to `hoursBreakdown`, so a Saturday or Sunday booking shows that day's rule. Web no longer has `combinedPaidHoursFromIntervals`; the merged clash-card total stays an iOS port until it moves here.

## Annual leave against bookings

`leaveCoverageRows` runs over the same coverage window as the other warnings and only looks at approved leave. Leave is FULL DAY, AM, or PM; anything else stored on a holiday document is treated as FULL DAY.

- **Booked during annual leave** (high). Any booking interval that overlaps the leave window. Full-day leave overlaps every booking that day. The row lists each booking and the overlapping minutes.
- **Half-day leave not covered** (medium). For AM or PM leave, the other half is the working half. Every booking interval that day is subtracted from it. Whatever is left is reported with clock ranges and hours. PM leave with a 07:30–09:30 custom booking on the default company reports "09:30–12:00 (2.5 hours) is not booked". No booking at all reports the whole half. The row respects `excludedUserIdsFromUnbookedWarnings` and `includeWeekendsForUnbookedLabour`; the clash row does not.

`unbookedLabourRows` already skips a person-day with any approved leave, so a half day produces exactly one warning: the cover row from this rule.

People are matched by account first (`userId`), then by any operative profile sharing the account's email. A roster operative without an account is matched by operative id.

## Dismissed warnings

An expired-qualification warning can be dismissed. The dismissal is `organizations/{orgId}/dismissedWarnings/{dismissKey}` where `dismissKey = qualificationDismissKey(operativeId, qualificationId, expiryDayKey)`. The key includes the expiry day, so saving a renewed certificate with a new date produces a fresh warning. Upcoming (not yet expired) rows are never hidden by a dismissal. Both apps read the collection and filter with `withoutDismissedQualificationRows`.

## Organisation context

One signed-in session has one current organisation id.

Web and iOS both call `chooseSessionOrganization` (and `provisionalOrganizationId` before probes finish). Order: explicit switch, then the company **this device** remembered, then `users/{uid}.organizationId`. A confirmed non-member is skipped. A slow, failed, missing, permission-denied, or unconfirmed first-tick / cache-only membership read is `unknown` (`orgAccessProbeFromReads` with `unconfirmed`) and must not throw away the remembered company. Do not invent a second picker that prefers the user document or an incomplete membership list.

Web remembers `pp.webActiveOrg:{userId}` (`webSessionOrganizationStorageKey`). iOS already remembers `cached_organizationId` — do not invent a second phone key. Switching writes that device key. Login persist is `persistOrganizationId` from the chooser: the remembered company when it wins; **null** when falling back to the user-document company — including when this device has no remembered key yet — so a remount that missed local storage or treated a cache read as denied cannot overwrite this device. Web must not write `users/{uid}.organizationId` on switch or login. iOS may keep writing that field on an explicit switch (existing `switchActiveOrganization` write) but must not copy it into `cached_organizationId` on restore. A restore / token refresh / new-bundle remount that opens the user-document company must leave the device key as it is.

The browser and the phone may show different companies. Each device has one active company. Same-user sign-out must keep the remembered key (`rememberedOrganizationSurvivesSignOut` / `shouldClearRememberedOrganization`). Clear only when a **different** account is about to use the same slot.

The switcher lists every company the user is a member of (`members.{uid}`, `creatorUserId`, `users/{uid}/orgMemberships`). That list is not the session chooser. `sessionMembershipIds` **always** unions discovered ids with remembered, user-document, explicit, and the last list — including when the members/creator query “finished” but omitted a company this device already knows. A finished query that dropped the other company is still a miss. Known company documents paint first (`onKnown`); the 12s members/creator scan must not hide them or delay the first list. “Logged into the other one” must not hide the missing company from the list.

## Switching organisation

Switching is not a single assignment.

1. Membership in the destination company is checked before its data is shown.
2. `adoptCurrentOrganization` advances the epoch on web. iOS replaces `organizationSwitchToken` and removes the previous organisation listener.
3. A Firestore listener started for company A does not call the callback that now belongs to company B (`lib/firebase/subscribeOrgCollection.ts`).
4. `runOrgLoad` does not keep a successful cache entry when the epoch changed during the request.
5. Booking creates and edits do not write the response into the store when the epoch changed.
6. iOS `SmartCacheService` and `PersistenceService` key memory and UserDefaults by the current organisation id, and by user id. Same-user sign-out must **not** clear `cached_organizationId`. Login restore calls `chooseSessionOrganization` with that key as `rememberedOrganizationId`. Clear the key only when a different uid signs in (`shouldClearRememberedOrganization`).

## Firebase authorisation

`canAccessOrganization` is membership in that organisation (the user document, the members map, or the creator). On the web rules, the platform owner account is also allowed — from 1.12.0 only the Auth token email `info@projectplanner.us` with `email_verified` (`isVerifiedPlatformOwner`), never a users document's `email`. From 1.12.0 a person that organisation has deactivated is not a member for the rules either (`organizationMemberActive`: their users document of that organisation `isActive: false`, or their membership there `accountActive: false`); the push Cloud Function uses the same function before it pushes a row, and the rules refuse an inbox row whose `userId` is not a member. A person's alias ids (`formerUserIds`, `sameEmailUserIds`) are written by admins and the invite placeholder copy only, and the rules read them only from the caller's own company's users document. A manager with operatives access writes only operative-only invitations (`invitationIsOperativeOnly`). An admin flag on the user document is not membership in every company. `organizationExists` is not access.

A signed-in user can still list organisation documents. The apps query that list with `members.{uid}` or `creatorUserId`. Tightening the list rule further has to stay compatible with those two queries. Subcollection reads and writes, and a direct read of another company's organisation document, are membership-scoped.

Other role gaps inside one company (for example who may edit settings) are listed in `project-planner-ios/app-tests/rules/firestore.rules.test.mjs`. Closing the cross-company hole does not by itself close those.

## First divergences this architecture closes

Warning counts differed because the scan window was calculated twice, and because qualification, unverified, and unbooked rows were selected twice. Web used the organisation time zone. iOS used `Calendar.current`, so a person outside the UK could be on a different calendar day, and an empty payment-run list fell back to days 1–2 instead of the half-month default. The shared window and the shared row functions are the fix. The count is whatever those functions produce from the same data, settings, and time zone. It is not copied from one screen onto the other.

Bookings booked for a pending invitee were stored under the placeholder id (`users/{UUID}`). Accepting the invite copies the profile to `users/{authUid}` and deletes the placeholder, so those bookings matched nobody: Daily Overview dropped the row and Warnings flagged the person as unbooked on the days they were booked. `formerUserIds` and `labourPersonIds` close that. Separately, the picker and the unbooked rule disagreed on who is labour (role-only admins were flagged but not bookable; users with no role flags were bookable but never flagged); both now use `labourBookingKind`. iOS additionally decoded `operativeId` as a UUID, so a web booking under a Firebase Auth uid never reached iOS Daily Overview or iOS Warnings.

A manager double booked on 22 Oct 2026 showed on iOS and not on web. The roster lists one row per email, and both bookings were saved under the other `users` document id on that email (the sign-in uid), which has no operatives catalogue row. Web's manager clash check matched manager bookings by exact user id and labour bookings only through the catalogue, and the Warnings page never passed `userIdAliases`, so both bookings belonged to nobody. `personDayItems` reads every stored id through `resolveBookingPerson` with the roster's `aliasIds` and `formerIds`; `lib/warnings/warningsComputation.test.ts` and the parity fixture lock it. Web also merged two job documents with one job number, so a booking on the second "C646" showed "Deleted job"; `workDocuments` keeps both.

Bookings differed for the same reason when a listener for company A could still publish into the store after a switch to company B, and when local caches were not keyed by organisation.

## File reports

"Report a problem with this file" is `lib/canonical/fileReports.ts`. A report is `organizations/{orgId}/fileReports/{reportId}` (uppercase UUID) with `organizationId`, `storagePath`, `surface`, `parentId`, `fileName`, `reason`, `details`, `reportedByUserId`, `status: 'open'` and a server `createdAt`. `fileReportWriteFields` builds it and refuses a path outside `organizations/{orgId}/`, an unknown `reason` (`FILE_REPORT_REASONS`) or `surface` (`FILE_REPORT_SURFACES`), or a missing parent. `fileReportStoragePath` turns a download URL into the Storage path; the download URL and its token are never stored. Details are capped at `FILE_REPORT_DETAILS_MAX`. Reason and status labels are `fileReportReasonCopy` and `fileReportStatusCopy`. `canReviewFileReports` is admins and super admins; they close a report with `fileReportReviewWriteFields` (`reviewed` or `removed`, plus `reviewedByUserId` and a server `reviewedAt`). Firestore rules let anyone in the organisation create a report as themselves, let only admins and the platform owner read and close it, and never allow delete. The link appears on site audit photos, task attachments, health and safety files, deadline files, variation evidence, and another person's qualification certificates. Profile photos and company logos are not reportable.
